# 第 11G 课：控制范围与 AI 全栈协作清单

本课原计划继续实现“评分正式提交”。经过需求拆解后决定停止开发，因为当前项目的评分、鉴权、数据库、文件、部署和监控链路已经能够支撑学习目标。继续增加业务功能会扩大维护成本，但不会解决新的核心知识缺口。

能够判断“这个功能现在不值得做”，是 AI 开发中必须由人承担的责任。AI 很擅长继续生成代码，却不会自动替项目控制范围。

## 1. 什么时候值得继续实现

满足以下任一情况时，可以继续开发：

- 真实业务或客户明确需要；
- 能验证一项尚未掌握的关键能力；
- 能解决已经发生的问题或明显风险；
- 是交付、验收或面试展示必需的完整链路。

以下情况应优先停止：

- 只是为了让练习项目看起来功能更多；
- 新代码主要重复已经跑通的模式；
- 没有用户、验收条件或使用场景；
- 引入的数据迁移、权限和维护成本高于学习收益；
- 当前真正的短板是理解已有代码，而不是缺少功能。

## 2. 交给 AI 前的需求卡

以后收到需求时，至少先确认：

```text
目标：要解决谁的什么问题？
业务规则：什么允许，什么禁止？
权限：谁能看、谁能操作？
数据：保存什么，历史数据怎么办？
异常：失败时用户看到什么，是否允许重试？
兼容：旧前端、旧接口、旧数据是否受影响？
明确不做：本次范围之外是什么？
验收条件：用什么可观察结果证明完成？
```

不确定项应先询问产品、后端、运维或客户，不能让 AI 随机选择。

## 3. 让 AI 修改前先要影响分析

要求 AI 在写代码前回答：

- 会修改哪些前端组件和 API 封装；
- 会修改哪些 Controller、DTO、Guard 和 Service；
- 是否修改 Prisma Schema，是否需要迁移；
- 是否影响已有数据、接口调用方和部署方式；
- 需要什么单元测试、集成测试和手工验收；
- 是否涉及权限、Secret、文件访问或破坏性操作。

如果影响范围明显超过需求，应先缩小方案，而不是直接接受更多代码。

## 4. 开发过程中的固定检查

### 需求与代码

- 每处修改都能对应一条需求或验收条件。
- Controller 只负责接收和转交请求，业务规则主要位于 Service。
- 前端校验改善体验，后端仍执行可信校验。
- 不把用户 ID、角色或权限结果直接相信为请求体数据。

### 数据

- 修改 Schema 前阅读迁移 SQL。
- 判断是否删列、改类型、丢数据或导致旧数据不符合新约束。
- 文件元数据与 MinIO 对象的创建、删除是否保持一致。
- 不对真实数据执行未经确认的删除、恢复或 `down -v`。

### 运行环境

- 先确认当前请求进入 Vite 还是 Nginx、Windows 进程还是 Docker 容器。
- 修改源码后判断是否需要热更新、重启进程或重新构建镜像。
- 不能用“源码已经改了”推断“线上运行的就是新版本”。

### 验证

- TypeScript 检查证明类型能通过，不证明业务正确。
- 单元测试验证被隔离的规则，不证明真实依赖可用。
- 集成测试验证 HTTP 与真实依赖协作，不代替页面体验检查。
- 手工验收记录 URL、Method、Status、Payload、Response 和 Request ID。
- 发布后还要检查健康状态、日志、指标和关键业务请求。

## 5. 出错时给 AI 的证据模板

```text

当前运行模式：Vite / Docker Nginx
URL 和 Method：

Response code 和 message：

```

先提供证据能减少 AI 修改错误层级的概率。

## 6. 本项目最后一次实验说明了什么

评分说明功能第一次手工测试时，新 React 页面已经出现，但绕过页面提交 201 字仍返回 200。最终证据表明：

```text
浏览器 → 新版 Vite 前端 → 旧版 Docker API → PostgreSQL
```

重新构建 API 镜像后，同一请求返回 400 和 `FEEDBACK_TOO_LONG`。这证明全栈验收还必须确认运行版本和请求路径，而不能只看页面变化。

## 7. 可重复使用的 AI 任务提示词

```text
我是主要通过 AI 开发的前端转全栈开发者。请先复述需求，并列出不明确的业务规则、修改范围、数据与兼容风险，不要立即写代码。

规则确认后再小步实现。每次说明修改了什么、为什么修改，并指出对应的前端、API、Service、数据库和测试文件。涉及数据库迁移、删除数据、生产环境、Secret 或外部系统写操作时必须先停下说明风险。

完成后执行与风险相称的类型检查、单元测试和集成测试，并告诉我每项验证证明了什么、没有证明什么。最后给出需要我在 Network、日志、数据库、容器或页面中手工确认的验收项。
```

## 8. 本课结论

- 会让 AI 写代码只是起点，会判断是否应该写才是项目能力。
- 不需要背框架 API，但必须理解业务、权限、数据、运行环境和验证边界。
- Demo 达到学习目的后应停止堆功能，把时间用于真实薄弱项。
- 遇到真实任务时，再按需求补充技术，比提前堆积陌生框架更有效。

至此，项目预定的 AI 全栈核心路线完成。后续不再为了课程增加业务功能，改为用现有数据做只读 SQL、代码阅读和故障分析练习。
